APLICAR SISTEMA VISUAL UNIFICADO A TODOS LOS CASE STUDIES DEL PORTFOLIO

Quiero establecer un sistema visual consistente para TODAS las páginas de Case Study del portfolio.

Actualmente los proyectos incluyen:

MIRA APP
ONCOBOT
PROJECT BUILDER

Este sistema debe aplicarse a todos los Case Studies existentes y también debe utilizarse como regla para futuros proyectos.

IMPORTANTE:

No quiero rediseñar los Case Studies desde cero.

No modificar la estructura narrativa existente.

No cambiar el contenido de los proyectos.

No inventar información.

No inventar estadísticas.

No inventar métricas.

No inventar resultados de investigación.

No transformar hipótesis en resultados reales.

No agregar datos que no hayan sido proporcionados explícitamente.

El objetivo es crear una identidad visual común entre todos los Case Studies, manteniendo el contenido y las particularidades de cada proyecto.

━━━━━━━━━━━━━━━━━━━━
01. JERARQUÍA DE SECCIONES
━━━━━━━━━━━━━━━━━━━━

Todas las secciones de todos los Case Studies deben utilizar el mismo sistema editorial.

Ejemplo:

01
RESUMEN

02
EL PROBLEMA

03
INVESTIGACIÓN

04
INSIGHTS

05
SOLUCIÓN

etc.

El número de sección debe ser pequeño y funcionar como metadata.

El nombre de la sección debe ser mucho más grande y tener protagonismo.

USAR:

Número:
14–16px
Peso 500–600

Título de sección:
40–48px
Space Grotesk
Peso 700

Tablet:
32–40px

Mobile:
28–34px

Los títulos de sección NO deben parecer pequeños botones o badges.

Si se utiliza un rectángulo de color detrás del título, debe funcionar como elemento editorial y no como botón.

Mantener las esquinas predominantemente rectas.

━━━━━━━━━━━━━━━━━━━━
02. BLOQUES DESTACADOS / MÉTRICAS
━━━━━━━━━━━━━━━━━━━━

Los bloques de información destacada deben utilizar una apariencia visual diferente de las tarjetas de contenido normales.

Usar un fondo ligeramente contrastante respecto al fondo principal de la sección.

Para fondos Dark Indigo:

Fondo principal:
#23003F

Fondo de bloques:
usar una variación ligeramente más clara del Dark Indigo, manteniendo la misma familia cromática.

Texto principal:
#FAFAFA

Acentos:
#BCAACF
#F94500
#FFFFB4

NO utilizar blanco puro como fondo de estas tarjetas.

NO utilizar gradientes.

NO utilizar glassmorphism.

NO utilizar sombras genéricas de tarjetas SaaS.

Los bloques deben sentirse editoriales y parte del sistema Neo-Brutalist del portfolio.

Borde:

1–2px sólido y sutil.

Border radius:

0–4px.

━━━━━━━━━━━━━━━━━━━━
03. REGLA PARA MÉTRICAS Y ESTADÍSTICAS
━━━━━━━━━━━━━━━━━━━━

MUY IMPORTANTE:

Nunca inventar cifras para hacer que una sección se vea más atractiva.

Nunca crear estadísticas ficticias.

Nunca utilizar frases como:

"+1,2M"

"85%"

"73%"

"40%"

"Alta tasa de abandono"

o cualquier otra métrica

si esa información no está explícitamente documentada en el contenido del proyecto.

Si una métrica existe y fue proporcionada por la diseñadora, puede destacarse visualmente.

Si una métrica NO existe:

NO inventarla.

En ese caso utilizar bloques editoriales basados en información real del proyecto.

Por ejemplo:

PROBLEMA PRINCIPAL

NECESIDAD DETECTADA

INSIGHT CLAVE

OPORTUNIDAD

DECISIÓN DE DISEÑO

HALLAZGO

En MIRA, eliminar o reemplazar cualquier estadística que no tenga una fuente o respaldo dentro de la investigación real del proyecto.

El Case Study debe transmitir credibilidad profesional.

━━━━━━━━━━━━━━━━━━━━

━━━━━━━━━━━━━━━━━━━━

Las tarjetas que contienen problemas, insights, hallazgos u oportunidades deben tener un sistema visual común.

Cada tarjeta debe incluir:

01
TÍTULO DEL HALLAZGO

Descripción breve.

02
TÍTULO DEL HALLAZGO

Descripción breve.

etc.

Los números deben funcionar como elementos editoriales.

Los títulos de estas tarjetas deben tener mayor tamaño y peso para facilitar el escaneo.

Título:

18–22px

Space Grotesk

Peso 700

Body:

16–18px

Inter

Line-height:

1.4–1.5

No utilizar textos demasiado pequeños.

La prioridad visual debe ser:

Número
↓
Título
↓
Descripción

━━━━━━━━━━━━━━━━━━━━

Además del título principal de cada sección, todos los subtítulos importantes deben tener una jerarquía clara.

H2:

32–40px

H3:

24–32px

H4:

20–24px

Body:

17–18px

Caption:

14–16px

Los Case Studies deben poder leerse cómodamente en desktop y mobile.

━━━━━━━━━━━━━━━━━━━━
06. INFORMACIÓN DEL PROYECTO
━━━━━━━━━━━━━━━━━━━━

El bloque que contiene:

ROL
DURACIÓN
FECHA
ENFOQUE
HERRAMIENTAS
TIPO

debe utilizar el mismo sistema en todos los Case Studies.

DESKTOP:

6 columnas en una sola fila.

ROL | DURACIÓN | FECHA | ENFOQUE | HERRAMIENTAS | TIPO

Utilizar únicamente divisores verticales entre columnas.

NO utilizar:

línea superior
línea inferior
borde exterior
borde alrededor del bloque

El primer elemento no debe tener borde izquierdo.

El último elemento no debe tener borde derecho.

Mantener espacio inferior suficiente antes de comenzar la siguiente sección.

Desktop:

6 columnas × 1 fila

Tablet:

3 columnas × 2 filas

Mobile:

1 columna × 6 filas

En mobile se pueden utilizar separadores horizontales entre elementos si son necesarios para mantener la legibilidad.

11. IMÁGENES Y MOCKUPS
━━━━━━━━━━━━━━━━━━━━

Las imágenes reales de cada proyecto deben tener protagonismo.

Cuando se utilicen pantallas de producto:

NO modificar el contenido de las pantallas.

NO cambiar textos.

NO cambiar colores.

NO modificar botones.

NO modificar datos.

NO rediseñar las interfaces originales.

Las pantallas deben mostrarse dentro de mockups de dispositivos cuando tenga sentido.

Los mockups deben ser limpios y editoriales.

No agregar explicaciones innecesarias alrededor de las imágenes.

Las imágenes deben tener suficiente tamaño para que puedan analizarse visualmente.

números de sección
espaciado
estructura de información
estilo de tarjetas
bordes
responsive

screens

diagramas
metodología
investigación

La identidad del portfolio debe funcionar como sistema contenedor.

━━━━━━━━━━━━━━━━━━━━
14. REGLA PRINCIPAL
━━━━━━━━━━━━━━━━━━━━

El objetivo es que una persona pueda entrar a cualquiera de los Case Studies y reconocer inmediatamente que pertenece al mismo portfolio.

Debe sentirse:

EDITORIAL
CREATIVO
PROFESIONAL
EXPERIMENTAL
HUMANO
ESTRATÉGICO

No debe sentirse como una plantilla generada automáticamente.

Priorizar siempre:

CONTENIDO REAL
CLARIDAD
JERARQUÍA
LEGIBILIDAD
CONSISTENCIA

antes que decoración.

NO modificar información existente salvo que sea necesario eliminar una estadística o afirmación que no tenga respaldo explícito en el contenido proporcionado.

Aplicar este sistema visual globalmente a todos los Case Studies existentes.
